### 6. H5 修改密码 —— ✅ 已整改

**初查结论**：`PUT /h5-api/user/resetpwd` 直接用 `user.setPassword(user.getPassword())` 覆盖，**不校验原密码、无复杂度校验**。任何持有有效 token 的人（如 token 被窃取）可直接改密接管账号。

**是否整改**：已完成，且初查时识别的三项残留风险一并收口。

#### 6.1 原密码校验 + 复杂度校验

| 文件 | 改动 |
|------|------|
| `ruoyi-common/.../utils/PasswordPolicy.java`（新增） | 密码复杂度策略统一入口，`check()` 返回 null 表示通过，否则返回失败原因；规则 ≥8 位且含小写、大写字母和数字 |
| `ruoyi-system/.../domain/H5ResetPwdDTO.java`（新增） | 改密入参 `oldPassword` / `newPassword` |
| `IH5UserService` / `H5UserServiceImpl` | 新增 `changePassword(userId, old, new)`：校验原密码 → 校验复杂度 → 新旧不可相同 → 复用 `resetPassword`（内部 BCrypt） |
| `H5UserCenterController` | `resetpwd` 改收 DTO，参数缺失返回「参数不完整」，业务校验全部在 Service |
| `H5LoginServiceImpl` | 注册时的复杂度校验改为复用 `PasswordPolicy`，与改密同一口径 |
| `h5/src/views/user/Index.vue` | 改密弹窗改为「原密码 / 新密码 / 确认密码」，`before-close` 提交（失败保持弹窗打开） |

#### 6.2 改密后下线全部会话

H5 token 原为 `h5_login_tokens:{uuid} -> userId` 单点结构，无法按用户批量失效。新增用户维度索引：

| 键 | 类型 | 说明 |
|---|---|---|
| `h5_login_tokens:{uuid}` | String | token 本体（沿用原键名与纯字符串序列化，存量 token 不受影响） |
| `h5:user:tokens:{userId}` | Set | 该用户全部 uuid，随最后一个 token 一同过期 |
| `h5:pwd:retry:{userId}` | String | 原密码错误次数计数器 |

- 新增 `ruoyi-system/.../token/H5TokenStore.java`：`save` / `getUserId` / `remove` / `removeAllOfUser`。独立成组件是为了避免 `H5LoginServiceImpl` 与 `H5UserServiceImpl` 循环依赖。
- 下线动作放在 `resetPassword` 而非 `changePassword`，使「用户自助改密」与「后台管理员重置密码」共用同一收口。
- 前端改密成功后清除本地 token 并跳转登录页（本次请求的 token 同样已被服务端下线）。

#### 6.3 原密码失败锁定

- 计数键 `h5:pwd:retry:{userId}`，Redis `INCR` 原子自增，固定窗口（首次计数设 TTL，`getExpire` 兜底无 TTL 键）。
- 阈值复用 `user.password.maxRetryCount`（5 次）/ `lockTime`（10 分钟）。
- 超限直接返回「原密码错误次数过多，请10分钟后再试」，不再执行密码比对；改密成功清空计数。

#### 6.4 后台重置密码复杂度

- 复杂度校验下沉到 `H5UserServiceImpl.resetPassword`，`PUT /points/h5user/pwd` 与 `PUT /h5-api/user/resetpwd` 共用。
- `ruoyi-ui/src/views/points/h5user/index.vue` 表单规则由「6~20 位」改为 `^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{8,20}$`。

**接口变更（破坏性）**
`PUT /h5-api/user/resetpwd` 请求体由 `{ "password": "新密码" }` 改为 `{ "oldPassword": "原密码", "newPassword": "新密码" }`。只传 `password` 的旧调用返回「参数不完整」，属预期行为，其他调用方需同步升级。

**当前现状**
原密码错误 → 不修改并累计次数；复杂度不足 → 返回具体原因；新旧相同 → 拒绝；全部通过 → BCrypt 加密后仅更新 `t_user.password`，同时下线该用户全部会话。

**仍存在的边界**：改造前已签发且未过期的 token 不在用户索引中，改密后无法批量下线，最长残留至 7 天 TTL（一次性过渡问题）。

### 7. JWT 签名密钥 —— ✅ 已整改

**初查结论**：`token.secret` 为若依默认值 `abcdefghijklmnopqrstuvwxyz`，后台（HS512）与 H5（HS256）共用同一密钥。密钥随配置文件走，任何能看到配置的人都能伪造任意用户（含 admin）的合法 token。

**是否整改**：已完成。**密钥已更换为随机串**（**初查时"为若依默认弱密钥"的描述已失效**）。

**当前现状**：当前值为 32 位随机串，已脱离默认值，伪造 token 的前提不再成立。

**建议**：生产环境通过环境变量/配置中心注入，不落 Git；后续如需进一步提高强度，可换为 48 字节以上的 Base64 随机串（更换后所有在线用户需重新登录，需择机执行）。

### 9. H5 token 时效 —— ✅ 已整改

**初查结论**：JWT 只放 `h5_uid` + `userId`，**无 `exp`**，失效完全依赖 Redis 键 TTL（7 天）。

**是否整改**：已完成。

**如何修改**
- `createToken` 增加 `setIssuedAt` / `setExpiration`，有效期与 Redis TTL 共用同一份配置 `h5.token-expire-minutes`（默认 10080 分钟 = 7 天）。
- TTL 统一由 `H5TokenStore.getExpireMinutes()` 提供，JWT 与 Redis 不会错位。
- 如需缩短有效期，只改 `application.yml` 一处即可，无需动代码。

**实测**（jjwt 0.9.1 + JDK 17）
- 新 token：`exp` 剩余 6.9999 天，`iat` 正常写入。
- 过期 token：`parseClaimsJws` 抛 `ExpiredJwtException` → `getLoginUser` 返回 null → 拦截器 401。
- **历史无 `exp` 的 token 仍可正常解析**（`exp=null`），升级不会导致存量用户掉线。
- 附带确认：jjwt 反序列化后 `userId` claim 实际类型是 `Integer`，故 `logout()` 中取用户 ID 用 `Long.valueOf(claim.toString())` 而非强转。

**token 传输**：从 `Authorization: Bearer` 或 `h5-token` 头读取，前端双头携带，兼容处理无问题；token 存 localStorage，当前未发现渲染用户输入 HTML 的用法。

### 11. H5 密码登录防爆破 —— ✅ 已整改

**初查结论**：密码登录有图形验证码，但无账号/IP 级失败锁定（后台有 5 次锁定）。

**是否整改**：已完成。

| 维度 | 键 | 策略 |
|---|---|---|
| 单账号 | `h5:login:fail:{phone}` | 失败 5 次锁定 10 分钟（复用 `user.password` 配置） |
| 单 IP | `h5:login:ip:{ip}` | 每分钟最多 20 次尝试（配置 `h5.login-ip-max-per-minute`） |

- 计数使用 Redis `INCR` 原子自增，`ensureExpire` 兜底无 TTL 键，避免永久锁定。
- **IP 阈值刻意比账号阈值宽松**（20 次/分钟）：公司、校园、商场 WiFi 属 NAT 出口，多人共用同一 IP，阈值过严会大面积误伤正常用户。真正防定向爆破的是账号维度。
- 登录成功清空账号维度计数；与图形验证码形成双层防护。

### 12. 对外接口 `POST /scan/scan` —— ⚠️ 业务确认暂不整改

**初查结论**：`JsocnMarketShopScanController` 的 `POST /scan/scan` 标注 `@Anonymous`，`SecurityConfig` 亦对 `/scan/scan/**` 匿名放行 —— 匿名可向扫码统计表写数据，`ip`、`userAgent`、`startTime` 均可由客户端伪造，无限流、无字段白名单。

**是否整改**：**业务确认暂不修改**。该接口用于采集扫码上报信息，为保证信息获取的完整性，暂不施加限流与字段白名单。

**风险接受说明**
- 残留风险：统计表可能被刷入脏数据，影响报表准确性；不影响账号与业务数据安全（该接口不读取、不修改用户数据）。
- 若后续需要收敛，建议：按 IP 加限流（如 60 次/分钟）+ 只接收白名单字段（忽略客户端传入的 `ip`、`userAgent`，改由服务端获取）。

### 13. CORS —— ⚠️ 业务确认暂不整改

**初查结论**：`ResourcesConfig.corsFilter()` 中 `addAllowedOriginPattern("*")`、`addAllowedHeader("*")`、`addAllowedMethod("*")`，允许任意来源跨域。

**是否整改**：**业务确认暂不修改**，保留当前配置。

**风险接受说明**
- 当前接口鉴权基于 `Authorization` 头中的 JWT（非 Cookie），浏览器不会自动携带凭证，因此"任意 Origin"不会直接造成会话劫持（不同于 Cookie 会话模型下的 CSRF 型风险）。
- 残留风险：任意第三方站点可调用公开接口、可读取公开数据；若后续引入 Cookie 会话或敏感接口，需重新评估。
- 若后续需要收敛，建议改为显式域名白名单（H5 域名 + 后台域名），并保留 `allowCredentials=false`。

### 14. XSS 过滤 —— ✅ 已整改

**初查结论**：`xss.urlPatterns` 只含 `/system/*,/monitor/*,/tool/*`，未覆盖 `/h5-api/**`，H5 用户写入的昵称、姓名、地址等文本不受过滤。

**是否整改**：已完成。

```yaml
xss:
  enabled: true
  excludes: /system/notice,/h5-api/auth/*,/h5-api/user/resetpwd
  urlPatterns: /system/*,/monitor/*,/tool/*,/h5-api/*
```

**为什么必须排除两个路径**：实测 `EscapeUtil.clean("Abc<123>def")` 返回 `Abcdef`——尖括号内容会被当作标签剥掉。若把登录/改密接口纳入过滤，**密码里含 `<`、`>` 的用户将无法登录或改密**。故排除 `/h5-api/auth/*`（登录、注册）与 `/h5-api/user/resetpwd`（改密），这两处只接收手机号/密码/验证码。

**覆盖范围**：`/h5-api/user/profile`（昵称、姓名、头像）、`/h5-api/user/addresses`（收货人、地址）等用户可写入文本的接口均已纳入。

**已知限制**（沿用若依原生实现，非本次引入）
- 过滤是对整段 JSON 字符串做 HTML 清洗。实测 `{"name":"a<b>c"}` 会被清洗成 `{...,"name":"a<b>c"}</b>`，多出的闭合标签会导致 JSON 解析失败并返回 400。
- 即文本中含类 HTML 片段时请求会被**拒绝**而非静默净化：安全上无绕过风险，体验上是报错。
- 双引号不会被转义（`validateEntities` 在 `filter()` 中已注释停用），正常 JSON 结构不受影响——实测清洗前后双引号数量一致。
- `XssFilter` 对 GET/DELETE 一律跳过，仅过滤 POST/PUT/PATCH。
